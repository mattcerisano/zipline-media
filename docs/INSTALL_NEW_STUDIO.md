# Installing Studio OS for a new studio

How a second production company gets its own copy of the Command Center:
its own database, its own deployment, its own sign-ins, nothing shared with
anyone else's. Budget an hour, most of it waiting for Supabase and Vercel to
provision. No code changes are needed; everything that names the studio is an
environment variable, and every one of them is optional.

What you end up with: `https://<your-project>.vercel.app` that opens straight
on the login screen (no marketing site), one admin account, and a database
with sample productions, clients and crew to look at before adding real ones.

You need accounts at [supabase.com](https://supabase.com) and
[vercel.com](https://vercel.com) (free tiers are fine for a pilot), a GitHub
account to hold your copy of the code, and `node` 20+ on your machine for
step 5.

---

## 1. Create the Supabase project

1. Supabase → **New project**. Pick a name, a database password (you won't
   need it again; the app uses API keys), and the region closest to you.
2. Wait for it to finish provisioning (a minute or two).
3. **Project Settings → API**. Keep this page open — step 5 needs the
   **Project URL**, the **anon public** key and the **service_role** key.

## 2. Install the database

1. **SQL Editor → New query**.
2. Paste the whole of [`supabase/install/install.sql`](../supabase/install/install.sql)
   and click **Run**. It is one file: every table, policy, storage bucket and
   function the app uses, in order. It takes a few seconds and ends with a
   notice counting the migrations it recorded (69 at the time of writing).
3. Optional but recommended for a pilot: new query, paste
   [`supabase/install/sample_data.sql`](../supabase/install/sample_data.sql),
   run. Three clients, four productions, six crew, some gear and one drive, so
   the first sign-in isn't a wall of empty tabs. Every sample production is
   titled "[Sample] …" and the dashboard says so until they are gone;
   [`remove_sample_data.sql`](../supabase/install/remove_sample_data.sql)
   clears them in one go.

`install.sql` is generated from the migrations folder by
`node scripts/build-install-sql.mjs`; if you ever pull newer code, re-run the
newer migrations as described in [MIGRATIONS.md](MIGRATIONS.md).

## 3. Create the first admin

1. **Authentication → Users → Add user → Create new user**. Enter the admin's
   email and a password, tick **Auto Confirm User**.
2. **Authentication → Sign In / Providers → Email**: turn **Allow new users
   to sign up** *off*. Accounts are created by an admin from inside the app
   (Settings → Team); nobody should be able to make their own.
3. **SQL Editor → New query**, paste
   [`supabase/install/first_admin.sql`](../supabase/install/first_admin.sql),
   change the email on its first line to the one from step 1, run.

Alternatively set `OWNER_EMAIL` in step 5 to that address: it is let in as
admin whether or not the SQL ran. Doing both is fine.

## 4. Create the Vercel project

1. Fork or push this repository to your own GitHub account.
2. Vercel → **Add New → Project** → import that repository. Framework
   preset: Next.js (detected). Don't deploy yet; the first build fails without
   the Supabase keys, which is harmless but a wasted minute.
3. If Vercel asks for a root directory, it's the repository root.

## 5. Set the environment variables

From a clone of the repository on your machine:

```bash
bash scripts/setup-env.sh
```

It logs you into Vercel, links the folder to the project you just made, and
prompts for everything below. Secrets are read with echo off and sent straight
to Vercel. Press Enter to skip anything optional. Re-running later is safe (it
replaces, never duplicates).

Or set them by hand under Vercel → Project → **Settings → Environment
Variables**. Either way, **set them before the first deploy**: most are read at
build time.

### Required

| Variable | Value |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL from step 1 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon public key |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role key (server-only; never shared) |
| `OWNER_EMAIL` | the admin's email, unless you ran `first_admin.sql` |
| `STUDIO_ONLY` | `1` — makes `/` open the app instead of the marketing site |
| `NEXT_PUBLIC_STUDIO_NAME` | your studio's name (login screen, PDFs, calendar footers) |
| `SITE_URL` | the deployment's address, e.g. `https://acme-studio.vercel.app`; no trailing slash |

### Generated by the script (set them yourself if going by hand)

| Variable | Purpose |
|---|---|
| `CRON_SECRET` | protects the calendar-sync cron (`vercel.json`); any long random string |
| `CALENDAR_FEED_TOKEN` | makes the ICS feed URL secret; any long random string |
| `OAUTH_STATE_SECRET` | signs OAuth round-trips; any long random string |

### Optional — each switches on one feature

| Variable | Feature | Without it |
|---|---|---|
| `STUDIO_TIMEZONE` | IANA zone the call times are in (default `America/New_York`) | Eastern time |
| `NEXT_PUBLIC_STUDIO_HOME` | map centre as `lat,lng` | Midtown Manhattan |
| `NEXT_PUBLIC_STUDIO_EMAIL_DOMAIN` | your mail domain, for placeholders | domain of `OWNER_EMAIL` |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` | Google Calendar sync, Gmail inbox, Drive — [GOOGLE_SETUP.md](GOOGLE_SETUP.md); the redirect URI is `SITE_URL` + `/api/auth/google/callback` | Integrations tab shows "connect" and nothing syncs |
| `GOOGLE_MAPS_API_KEY`, `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` | Locations map, address lookup, nearest hospital | map hides itself; addresses are plain text |
| `ANTHROPIC_API_KEY` | the suggest-only assistant | it hides itself |
| `QUICKBOOKS_CLIENT_ID`, `_SECRET`, `_ENVIRONMENT` | read-only billing on production cards — [SETUP.md](SETUP.md) | QuickBooks card says "not configured" |
| `VIMEO_ACCESS_TOKEN`, `FRAMEIO_DEVELOPER_TOKEN` | review-link previews | plain links |

Discord, Slack and Teams alerts need no variables; they are set up inside the
app under Integrations.

## 6. Deploy and sign in

1. Vercel → **Deployments → Redeploy** (or push any commit). About two
   minutes.
2. Open the deployment URL. With `STUDIO_ONLY=1` it lands on the login
   screen; otherwise go to `/command-center`.
3. Sign in with the email and password from step 3. The dashboard opens with
   the sample data notice at the top.
4. **Settings → Branding**: your name, logo and brand colour (the colour
   re-skins the whole app). **Settings → Team**: add your people; the
   **Drive keepers** field there is who drives come back to.

That's the install. [PILOT_CHECKLIST.md](PILOT_CHECKLIST.md) is what to do in
the first week.

---

## Later

**Custom domain.** Vercel → Domains. Then update `SITE_URL` and, if Google is
connected, `GOOGLE_REDIRECT_URI` and the matching URI in Google Cloud, and
redeploy.

**Updating to newer code.** Pull the upstream repository into your fork and
push; Vercel redeploys. Run
`node --env-file=.env.local scripts/migrations/check-applied.mjs` (after
`npx vercel env pull .env.local`) to list any new migrations, and paste them
into the SQL editor in the order shown.

**What's shared with the original studio: nothing.** Your Supabase project
holds your data and only your Vercel project reads it. The code is the same
code, which is the point of the pilot.
